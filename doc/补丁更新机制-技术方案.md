# DBNest · 库巢 — 增量补丁更新机制技术方案

> 目标：**功能更新时无需重新下载 200MB 的安装包、无需管理员权限、无需重装**，只下发变化的业务文件（~3~8MB）。

---

## 1. 为什么需要补丁更新

安装包 = Electron 运行时（`db-admin.exe` + Chromium DLLs，约 **200MB**） + 应用资源（`resources/app`，含 `server/` + `web/`，约 **3.2MB**）。

- Electron 运行时：随 Electron 版本升级才变（半年一次），体积大、下载慢、杀软扫描慢。
- 应用资源：每次功能迭代 / bug 修复都会变，而**它才是用户真正关心的更新内容**。

因此「补丁更新」= 只增量下发「应用资源」的变化部分，覆盖层（overlay）方式落地，原安装包/运行时不动。

---

## 2. 总体设计

### 2.1 资源解析优先级（overlay 优先）
应用启动时，业务资源目录 `APP_DIR` 按以下顺序解析：

1. **用户 overlay 目录**：`%APPDATA%\DBNest\app-overlay\`（若存在 `server/preview-server.cjs` 则优先）。
2. **安装基准目录**：`resources/app`（安装包自带，只读）。

> 用户可写目录天然不要求管理员权限；Program Files 下的安装目录保持只读，避免 UAC 弹窗与写保护冲突。

### 2.2 主进程改为「薄壳 + 运行时 require」
原方案把整个 server 内联进 `electron-main.cjs`（116KB），导致补丁无法更新 server 逻辑。

新方案：
- `electron-main.cjs` 只负责：窗口、IPC、解析 `APP_DIR`、注册 `api`/`patch` 通道、relaunch。
- 运行时 `require(APP_DIR/server/preview-server.cjs)` 加载业务 server（含全部 API 与补丁逻辑）。
- 由于 overlay 优先，当用户应用补丁后，重启即加载 overlay 内的新版 server/web。

### 2.3 增量协议（manifest + files）
补丁源是一个静态目录（HTTP），结构：

```
<patch-url>/
├── manifest.json        # 远程清单
└── files/               # 仅变更/新增文件（目录结构同 app）
    ├── server/preview-server.cjs
    ├── web/preview/index.html
    └── ...
```

`manifest.json` 示例：
```json
{
  "version": "1.0.2",
  "generatedAt": "2026-08-17T...",
  "files": {
    "server/preview-server.cjs": { "sha256": "....", "size": 12345 },
    "web/preview/index.html":     { "sha256": "....", "size": 67890 }
  },
  "remove": []            // 需删除的相对路径（如某文件在新版被移除）
}
```

**差异计算在客户端**：拉取远程 `manifest.json`，逐文件对比本地（overlay 优先）`sha256`：
- 本地无 → 新增（add）
- 本地 sha256 不同 → 变更（update）
- 远程在 `remove` 列表且本地有 → 删除（remove）

仅下载差异文件写入 overlay，并校验 sha256（`.part` 临时文件 + 原子改名）。

## 3. 数据流（桌面端）

```
用户点击「🔄 检查更新」
  → 前端 patch('check', {patchUrl})
  → 主进程 handlePatch('check')
       · 本地 manifest（overlay 优先）vs 远程 manifest.json
       · 返回 { localVersion, remoteVersion, needUpdate, changes:[{path,size,kind}] }
  → 前端展示变更清单 + 体积
用户点击「应用更新并重启」
  → 前端 patch('apply', {patchUrl})
  → 主进程 handlePatch('apply')
       · 下载 manifest.files 中每个文件到 overlay（带 sha256 校验）
       · 处理 remove 列表
       · 写 overlay 的 .dbnest-manifest.json（标记新版本）
  → 前端调用 relaunch()
  → 主进程 app.relaunch() → 重新启动 → resolveAppDir 命中 overlay → 新版本生效
```

Web 模式（HTTP server）下，`check` 走 `fetch` 远程 manifest（需补丁源允许 CORS）；`apply` 因浏览器无法写本地文件，提示改在桌面端更新或手动替换。

## 4. 安全与健壮性

- **路径校验**：`apply` 前断言 overlay 路径包含 `DBNest\app-overlay`，杜绝误写系统目录。
- **原子写入**：下载到 `.part` 临时文件，校验通过后才 `rename` 落盘；网络中断可重跑续传。
- **sha256 校验**：每个文件落地后比对远程清单，不一致则删除并报错。
- **不触碰运行时**：补丁范围仅 `server/` + `web/`；`node_modules` / exe / DLLs 一律不更新（避免原生模块/二进制错配）。
- **回滚简单**：删除 `%APPDATA%\DBNest\app-overlay\` 即可退回安装基准版本。

## 5. 生成补丁包（开发侧）

```bash
node build-patch.cjs --version 1.0.2 [--base <旧app快照目录>] [--out <输出目录>] [--remove a/b.js]
```

- 未提供 `--base` 时输出全量 manifest（客户端仍会按需比对，只下差异）；提供 `--base` 时 `files/` 仅含变更/新增，体积更小。
- 输出目录默认 `dbnest-patch-out/`（`manifest.json` + `files/`）。
- 部署：把该目录挂为任意静态 HTTP 服务，`DB_NEST_PATCH_URL` 或客户端填写其 URL 即可。

桌面端也可通过环境变量固定补丁源：`DB_NEST_PATCH_URL=https://your-cdn/dbnest-patch/`，免用户手动填。

## 7. 局限与后续

- **主进程壳本身（`electron-main.cjs`）不随补丁更新**：仅升级 Electron 版本或壳逻辑时才需重装安装包（低频）。
- **`node_modules` 不随补丁更新**：新增驱动依赖仍需安装包；如需支持，可把驱动放 `files/` 并在 overlay 内单独维护 node_modules（进阶）。
- 后续可加：自动检查（启动/定时）、增量断点续传进度条、补丁签名校验（防篡改）。
